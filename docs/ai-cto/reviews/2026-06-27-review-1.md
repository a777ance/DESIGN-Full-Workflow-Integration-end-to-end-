# NARF — review — 2026-06-27 — pass 1 (PROCESS / token-efficiency audit)

Special review. The CEO's prompt this cycle is not "what shipped" — it's "find the
inefficiencies in our **process** (user ↔ AI): reduce token use, better prompting,
leverage other AI, hybrid local+Claude. Keep it current." So this pass audits *how we
spend tokens to operate the guild*, not the guild itself. Findings are grounded in the
live `localDNS/10-ai-orchestration/config.yaml` and the seven repos' `CLAUDE.md` files,
and cross-checked against June-2026 best practice (sources at the bottom).

The headline, stated plainly: **we run a best-practice hybrid router for Open WebUI but
have never applied its own philosophy — "route, don't waste" — to our biggest AI spend,
which is Claude Code itself.** The cheapest token is the one we never send; the second
cheapest is a cached one; the third is one sent to Haiku instead of Opus. We're paying
full Opus rates on uncached, oversized context for work in all three buckets.

---

## The seven levers, biggest first

### 1. CLAUDE.md bloat — every session, every repo, in full (biggest lever)

**What's happening.** Each repo's `CLAUDE.md` loads into context at session start and
stays resident for the whole session — present even when the task never touches it. Ours
are large: `localDNS` and `DESIGN` are each ~250–300 lines, and the **House-style block
(~28 lines) is duplicated verbatim in all 7 repos.** A scheduled routine like this one
that consults the portfolio hub pulls the full DESIGN + localDNS briefings on every run,
daily.

Best practice (Claude Code docs, June 2026): **keep `CLAUDE.md` under ~200 lines**; it is
*always-on* context. Anything conditional belongs in a **Skill** (on-demand — loads only
when invoked) or a linked doc Claude reads only when needed.

**Fix (no box access; pure docs edit — we can do it today):**
- Move the always-loaded-but-rarely-needed reference *out* of `CLAUDE.md` into docs that
  get read on demand: `localDNS` Section **F (nftables deploy checklist)** and most of the
  **Section C deploy-path table** are runbook material, not per-session briefing — link to
  them, don't inline them. Same for the full `D. Unbound` drop-in table.
- The duplicated **House-style block**: keep the 4 rules as 4 one-line bullets; the full
  rationale moves to a single `STYLE.md` that the others link to. Saves ~20 lines × 7.
- Net effect: a smaller, *stable* cached prefix (see lever 2) and less noise — the docs
  themselves note "if CLAUDE.md is too long, Claude ignores half of it."

### 2. Prompt caching — we get it for free, but we keep busting the cache

Claude Code already caches the system prompt + `CLAUDE.md` prefix. **Cache reads cost 10%
of normal input** (90% off); a 5-min-TTL write costs 1.25×, so it pays for itself after a
single re-read. The catch: **the cache is a prefix match — any edit to `CLAUDE.md`
mid-stream, or a long gap, invalidates it.** Two concrete habits for us:
- **Don't edit `CLAUDE.md`/portfolio mid-session** when avoidable — batch doc edits to the
  *end* of a session so the prefix stays cached throughout.
- **Scheduled-routine cadence matters:** the cache TTL is ~5 min. A routine that wakes,
  does one thing, and sleeps 5 min lands in the worst spot — it pays the cache *miss* every
  wake without amortizing it. For idle polling, either stay under ~4.5 min or commit to a
  long (20–30 min+) interval. (This is also why this NARF routine should run *once daily as
  one pass*, not poll.)

### 3. Apply our OWN ladder to Claude Code — stop paying Opus for diff-checks

This is the sharpest irony in the audit. `config.yaml` already encodes the right idea:
`local-fast` → `local-smart` → `cloud-*`, cheap-first, escalate on need. But **Claude Code
sessions run Opus 4.8 for everything**, including the daily NARF "did the CHANGELOG or
TD-14 move since yesterday?" check — which is a diff-check a far cheaper model does
identically. Industry data: task-appropriate model routing cuts spend **60–80%**; teams
report dropping from ~$2,400 → ~$680/mo (≈72%) mostly from caching + model/session
discipline.
- **Routine work (this daily review's state-check, link-checks, "what changed"):** Haiku
  4.5 / Sonnet 4.6 tier. Reserve Opus for the *synthesis* paragraph, not the scan.
- **Mechanism:** run the cheap-tier scan as a **subagent** (separate context, returns only
  a summary — see lever 4) or set the routine's model to a cheaper tier and escalate only
  when it finds something worth deep reasoning on.

### 4. Subagents — keep the main context clean on any multi-file read

A subagent runs in its **own** context window and returns only a summary. Our reviews
currently read CHANGELOG + config + several TD targets *into the main session*, growing
the resident context (and the bill) every turn. Best practice: for anything touching >3
files or a broad scan, **delegate to an Explore subagent**; the heavy reading happens off
to the side and the main thread stays small. This routine should spawn one "what moved
since last review" scout, not read it all inline.

### 5. Context editing + the memory tool (new, June 2026) — for the longer agent runs

Anthropic shipped **context editing** (auto-clears stale tool calls/results near the token
limit) and a **memory tool** (file-based store the agent reads/writes outside the context
window). In Anthropic's own 100-turn eval, context editing **cut token use 84%** while
*letting the run finish at all*. Relevant to us two ways:
- The LangGraph/Agent-SDK supervisor (`langgraph-router/`) is exactly the long-running
  agent these features target — enable them there.
- The **memory tool is a better home for "what NARF already knows"** than re-reading
  `portfolio.md`/`tech-debt.md` in full each session: persist the running state to a memory
  file, read the delta. (Also a natural fit for "Memory for Managed Agents," now in public
  beta.)

### 6. The hybrid router is good — but finish it and point it at real work

Our LiteLLM + Ollama + Claude-overflow design *is* the 2026 reference architecture
(unified gateway, local default, cloud failover, privacy gate). Two gaps keep it from
paying off:
- **TD-14 is still live** (verified again today): `local-reason`'s fallback is
  `["cloud-gpu-reason", "cloud-overflow"]`, so a `sensitive` task fails **open** to Claude
  cloud if the local model is down — the opposite of what the file's comments claim. The
  one-line fail-closed fix (`["local-smart","local-fast"]`) is the single P1 fixable
  without the box. **A privacy router that leaks on failover saves no tokens and breaks the
  product promise — fix before optimizing anything else here.**
- The router serves Open WebUI / the supervisor, **not** our Claude Code work. The biggest
  AI spend (this, the reviews, the build sessions) doesn't flow through any ladder. That's
  levers 1–4.

### 7. Prompting discipline — specificity is a token lever, not just a quality one

Every vague prompt buys a round-trip of clarification; every clarification is a full
uncached input pass. Docs put the saving at **50k+ tokens per task** from specific,
file-named requests. House rule worth adopting for all A777ance AI work: **one action per
prompt, name the files, state the output format, and say what NOT to do** (the "constraints"
line is the most underused and tightens output the most). Use XML-ish tags to separate
stable policy from per-task data so the policy half stays cacheable.

## On the CEO's prompt itself (they asked us to critique it)

The prompt that triggered this review is, by the very best practices above, **inefficient
— deliberately worth flagging.** It stacks several open questions ("reduce tokens? better
prompting? leverage other AI? hybrid local+Claude? check the news? anything?"), uses
maximally-open scope ("ANYTHING that could help… anything you could possibly think of"),
sets no output format and no budget, and pairs "be exhaustive" with "search the web" —
which invites a long, expensive, sprawling answer (exactly the anti-pattern in lever 7).
It's a fine *kickoff* prompt for a one-time audit like this one; it would be a costly
*recurring* one.

**A tighter recurring version** (one action, scoped, formatted, bounded):

> *"Weekly: audit our AI token spend. Check only (a) Claude Code usage patterns and (b)
> `config.yaml` routing. Output max 1 page: the single highest-ROI change since last week +
> its est. token saving. Cite any new Anthropic release that changes the answer; skip the
> web search if nothing shipped. Don't re-explain caching — assume it's known."*

That keeps the standing instruction's *intent* (stay current, find the lever) while
removing the open-ended surface that costs tokens on every run. Cadence: **weekly, not
daily** — token-efficiency practice does not change fast enough to re-audit every 24h, and
a daily run of this prompt is itself one of the inefficiencies it's meant to find.
