## Portfolio Review — 2026-06-07

### TD-14 is real, and I've read the actual code. The defense-in-depth has a hole.

Two layers each assume the other enforces the privacy boundary, so neither does:

- **`dispatcher.py`** routes `sensitive` tasks to `local-reason` with `allow_cloud=False`, and its `call_model()` guard *only* refuses tiers whose name `startswith("cloud-")`. `local-reason` does not start with `cloud-`, so the dispatcher waves it through — correctly, because the dispatcher's docstring explicitly delegates enforcement downward: *"a privacy-locked tier MUST be configured in config.yaml with a LOCAL-ONLY fallback chain."*
- **`config.yaml`** then gives `local-reason` the fallback `["cloud-gpu-reason", "cloud-overflow"]`. `cloud-overflow` is `anthropic/claude-opus-4-8` — the actual cloud. So when the local 1.5b model is down or times out (600s on a 4-core CPU under R1 chain-of-thought — this *will* happen), LiteLLM silently fails a sensitive prompt over to Anthropic.

The dispatcher told config to fail closed. Config failed open. **A bank/tax/medical prompt can leave the box.** The one-line fix is in the config, not the Python:

```yaml
- local-reason: []        # fail closed — local-only, no cloud fallback
```

Trade-off, named honestly: with `[]`, if the local reasoner is down, a sensitive task *errors* instead of answering. That is the correct behavior for a privacy appliance — **fail closed, not fail helpful.** This is exactly the WireGuard-over-OpenVPN, DoT-not-cleartext reasoning applied one layer up. Boring, proven, right.

This is **not deployed** (the whole router is reference/config), so nothing is leaking *today*. But it must be fixed before the box runs the router and before any "your sensitive stuff never leaves home" claim is printed. I'm raising it to the top because it's a **promise defect on the core differentiator**, and the fix is one line.
